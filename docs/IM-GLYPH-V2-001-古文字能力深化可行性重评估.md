## 2. 背景与 V1.0 现状

### 2.1 V1.0 已交付的古文字能力（决策 D-V1-01 落地结果）

V1.0 采用"**受限字库 + 真实字形映射**"路径，已交付：

- **单一字源**：霞鹜篆书 LXGW Seal（OFL 1.1），子集化 165 篆字 / 238 今字映射，42KB woff2 静态托管。
- **渲染**：按 Unicode 18.0 小篆码位 `U+3D000+` 渲染；整字显现，不承诺笔顺（N1.4）。
- **边界处理**：字表外字符跳过并提示（`restricted:chars`）。
- **资产**：命名空间 `inkmotion-assets-v2`，同源回退 TTF（223KB，不预缓存）。

## 3. 字源分层策略（核心：解决 VR-02 + VR-01）

### 3.1 三层字源模型

| 层 | 字源 | 授权 | 字数 | 风格 | 角色 | 加载策略 |
|---|---|---|---|---|---|---|
| **L0 保底** | 霞鹜篆书 LXGW Seal | OFL 1.1 | 165 | 小篆 | 现状已集成，停止维护 | 必装（首屏可用） |
| **L1 主力** | 敬峰中山王篆 | OFL | ~2832（简）/ 2072（繁） | 战国中山王 | **覆盖常用字**，替代 L0 成为主力 | 按需（L1 可选包） |
| **L2 完整** | 全字库说文解字 | 台湾地区政府资料开放授权（可商用） | 6721 | 说文小篆 | 最大覆盖，低频/生僻字 | 按需（L2 包，已纳入 V2.0，体积大） |

> **设计决策 D-V2-01：** 沿用 V1.0 的"受限字库"哲学，但将"单字源"升级为"**分层多字源**"——L0 保证离线可用，L1/L2 按用户需要逐级加载，不进入首屏预算（避免 R-04 首屏体积回升）。

### 3.2 为何分层而非单一大字库

1. **可持续性（VR-02）**：L0 停维护后，L1（敬峰，OFL 持续可用）成为主力，消除单点依赖。
2. **体积可控（R-04）**：6721 字全量字体体积过大，必须按需；分层后首屏仍只有 L0 的 42KB 子集。
3. **风格一致性**：敬峰中山王篆与说文小篆风格相近（均属篆系），混排视觉冲突低于"篆+隶"混排；L2 仅在 L1 缺字时回退，保持主体风格统一。

### 3.3 合并映射与回退算法

- **码位统一**：三层均映射到 Unicode 18.0 小篆码位 `U+3D000+`（敬峰/全字库需做"今字→小篆码位"二次映射，类似 V1.0 的 `transformToSeal`）。
- **优先级**：`今字 → L1 命中？→ L0 命中？→ L2 命中？→ 跳过提示`。L1 优先于 L0（L1 覆盖更广且仍在维护）。
- **合并字表**：构建 `seal-map-v2.json`，记录每个今字的 `{l0,l1,l2}` 码位与"主呈现层"；`modernIndex` 扩展到三源并集。
- **越界规则不变**：三层均缺失的字符仍走 `restricted:chars` 跳过 + 提示（保持 V1.0 行为）。

### 3.4 工程实现要点

| 项 | 方案 |
|---|---|
| 字体子集化 | 敬峰/全字库需 pyftsubset 按已映射码位子集化；L1 目标 ≤ 300KB woff2，L2 允许更大但走独立缓存 |
| 资产命名空间 | 升至 `inkmotion-assets-v3`，新增 `seal-l1` / `seal-l2` 两项资产登记 |
| 加载管线 | 复用 V1.0 `fetchAssetCached` + `purgeLegacyAssetCaches`；L1/L2 懒加载，失败时静默降级到可用层 |
| UI | 设置页新增"篆书字源层级"开关（仅 L0 / L0+L1 / 全量），实时反映覆盖率预估 |

## 4. 隶书路径可行性（TBD-V1-03）

### 4.1 需求与约束

- V1.0 将隶书"评估后决定"，列入 V2 候选。隶书作为"篆→楷"过渡书体，是古典内容科普的高频需求。
- 约束：须为 **OFL / 开放授权**字体（V1.0 许可合规红线）；需建立"今字→隶书字形"映射。

### 4.2 候选字源（需 V2-C2 前 Spike 确认，TBD-V2-02）

| 候选 | 授权 | 说明 | 风险 |
|---|---|---|---|
| 开源隶书（如"书体坊隶书""方正隶书"开源版，需逐一核验授权） | 待核 | 需确认 OFL/可商用 | 授权不清则不可用 |
| 以现有楷体（UKai）+ 程序化隶变 | 自研 | 用笔画变形模拟隶书"蚕头燕尾"，无授权问题 | 质量低，非真实隶书 |
| 全字库隶书（若开放授权） | 开放授权 | 覆盖广 | 体积/可用性待核 |

> **建议方案（已按 D-V2-02 调整）**：依用户决策，**不再以合规确认为阻塞**——优先采用已发现的开放/可商用隶书字源；对授权状态未完全厘清的隶书字体，**一律采用并登记于「字体授权待办登记册」**，后续联系权利方获取正式授权。V2.0 将实际落地隶书映射与渲染（N2.2），而非仅留框架。

### 4.3 实现路径（已落地，V2-C2 N2.2）

- 新增 `FontFamily = 'li'`；`transformToLi(text, charset|null)` 今字→隶书码位映射（类比 `transformToSeal`）；**字表缺失时恒等映射**（`renderChars=Array.from(text)`、`outOfRange=[]`，不拦截）。
- 复用 V1.0 的"整字显现"渲染路径——`drawSealGlyph` 抽象为通用 `drawRestrictedGlyph(ctx,glyph,progress,color,fontStack?)`；隶书经 `drawLiGlyph` 委托，同样不承诺笔顺。
- 受限字集 UI 扩展：`LiCharsetPanel`（字表存在→网格；缺失→信息性提示"隶书字表未随包（待提供）"），Editor 并行提示块显示越界与覆盖率。
- 隶书路径独立模块 `src/lib/lishu.ts`（镜像 `seal.ts` 单层机制，不改写 V2-C1 既有测试与导出签名）。
- `StrokePathKind` 追加 `'li'`；`FONT_CATALOG` / `ASSET_MANIFEST` / `presets` / i18n / 授权登记册同步。

> 落地状态：**架构就绪、资产待提供**。字体二进制（`fonts/li/LiShu-Glyphs.woff2`、`LiShu-Regular.ttf`）与字表（`fonts/li/li-map.json`）未随包时，`loadLiCharset()`/`registerLiFont()` 静默返回 null/false，渲染回退系统隶书族（`LiSu`/`STLiti`）+ 衬线，**永不白屏/抛错**（资产缺失即静默跳过，V2 贯穿模式）。

## 5. 古文字轮廓描边动画可行性（TBD-V1-02）

### 5.1 定义澄清

V1.0 的 N1.4 已预留"整字显现 + **可选轮廓描边动画**"。此处"描边"指**沿字形轮廓的一次性描绘显现**（非逐笔笔顺，与 D-V1-01"不承诺笔顺"一致）。

### 5.2 实现路径（已落地，V2-C2 N2.3 —— 改为自研解析）

| 方案 | 原理 | 可行性 | 依赖 |
|---|---|---|---|
| ~~A. opentype.js 轮廓解析~~ | 用 `opentype.js` 解析 TTF 的 glyph outline，`stroke-dasharray` + `stroke-dashoffset` 动画 | 高（但否决） | **opentype.js ~80KB（gzip 前）会突破 V2 门禁（gzip<200KB）→ 否决** |
| **B′. 自研轻量 TTF 解析 + Canvas 弧长截断**（**最终采用**） | 自研 `src/engine/outline.ts` 解析 `glyf/loca/cmap/head/maxp`，得到轮廓点集与周长；Canvas2D **无 lineDashOffset 通用能力**（且需与导出帧一致），故按**累计弧长截断**描绘 | **高** | 零第三方依赖；仅覆盖 TrueType 简单/复合轮廓 |
| C. 预生成 SVG 序列 | 离线把每个篆字渲染为描边动画 SVG | 低 | 需全字预生成，维护成本高 |

> **最终方案 B′**：自研解析仅增加 **~2.75KB gzip**（构建 gzip 由 123.95KB → 126.70KB），远优于 opentype.js 的 ~80KB。零额外美术资源；描边动画作为"显现效果"开关（`ProjectOptions.outlineAnimation`），**默认关闭**（保证性能），用户可在"动画"设置中开启。

### 5.3 与 V1.0 渲染的关系（已落地）

- V1.0 古文字渲染为 `fillText` 整字填充。V2 在"描边模式"下改为：沿字形轮廓按弧长渐次 `stroke`，progress∈[0,1] 表示轮廓累计描绘完成度。
- 抽象统一为 `drawGlyphOutline(ctx, glyph, outline, progress, color, opts?)`（`src/engine/stroke.ts`）；**仅 seal/li 受限路径生效**（楷体逐笔/宋体淡入不受影响）。
- Canvas2D 无 `lineDashOffset` 的通用跨浏览器/导出一致性支持，故采用**弧长截断**：将轮廓展平为直线段序列（二次贝塞尔按固定子段采样），沿累计长度推进，在最后一段内插值收尾。
- **回退契约**：轮廓解析失败（CFF/OTF、无字形、损坏数据）→ 静默返回 null → `drawFrame` 回退整字填充；日志 `console.debug`（非 error），不污染用户控制台。
- **性能契约**：开关关闭或非受限路径 → **不做任何轮廓解析**（零开销，`preloadOutlines` 直接返回）。

## 6. 覆盖率与可持续性结论

| 维度 | V1.0 | V2.0（规划） |
|---|---|---|
| 篆书覆盖 | 165 字（L0 单源） | L0+L1 ≈ 2832 字（常用全覆盖）；+L2 6721 字（生僻） |
| 可持续性 | 单源停维护（VR-02 高） | 三源冗余，L1 持续维护（VR-02 降至低） |
| 书体 | 篆（受限） | 篆（分层）+ 隶（架构就绪、资产待提供） |
| 动画 | 整字显现 | + 可选轮廓描边（自研 TTF 解析，默认关闭） |
| 首屏体积 | 42KB 篆书子集 | 维持 42KB（L0）；L1/L2 按需不计入首屏；描边解析 +~2.75KB gzip |

> **结论 G-V2-01**：多字源分层在技术与授权上均可行，是 VR-02/VR-01 的根治方案；隶书与描边动画已在 V2-C2 落地实现路径（隶书资产待提供、描边采自研解析守门禁）。
